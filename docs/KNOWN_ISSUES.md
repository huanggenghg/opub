## 浏览器会话复用

**BROWSER-01：同一平台发布期间浏览器反复打开、关闭。状态：0.8.6 已实现会话合并；自动化回归覆盖，真实平台仍待复测。**

0.8.5 调用链：

1. `publish/orchestrator.py` 的发布编排先调用 `ensure_account_login`。
2. `publish/dispatch.py` 的登录检查调用平台 `cookie_auth`，多个平台会自行启动浏览器，检查后关闭。
3. 抖音等上传器的 `validate_upload_args` 又调用登录校验，再次启动、关闭浏览器。
4. `uploader/base_video.py` 的 `_browser_session` 正式发布时重新启动浏览器并创建上下文、页签，完成后关闭。
5. 登录失效时，登录、保存状态与再次校验也可能使用额外浏览器。这次逐个平台使用独立 CLI 进程测试，进程之间也没有共享会话。

这些开关是实现选择，并非平台强制要求。0.8.6 实现范围：

- 浏览器生命周期按每素材、每平台、每账号管理；同平台同账号的检查、必要登录、上传、结果确认复用同一个上下文和页签，通过页面跳转继续流程。
- 避免单独开浏览器做重复登录检查，在实际上传页检查登录状态；文件和参数校验保持为本地操作。
- 跨平台或跨账号保留独立的登录状态管理；B站继续使用 biliup 子进程，不套用浏览器会话。
- 正常完成或异常后统一关闭；本次不提供调试保留窗口选项。跨 CLI 进程保留窗口需要常驻会话/连接管理，不能仅删除 `browser.close()`，因为退出 `async_playwright()` 和进程结束也影响生命周期。
- 会话复用只减少重复开关和重建登录状态，不能据此假定 CDN 请求失败或页面识别问题会自动解决；提交结果未知保护必须继续保留。

验证范围：登录检查到发布不重复启动浏览器、扫码后沿用当前页签、不同账号状态互不覆盖、取消及异常正确释放资源、结果未知时不重复提交。

低优先级后续项：若二维码图片已写入，但随后的本地解码、终端输出或回调在保存函数返回前异常，可能遗留一张临时 PNG。该情况不影响登录、投稿安全或重试结果，后续可让各平台保存函数在部分失败时自行清理。
