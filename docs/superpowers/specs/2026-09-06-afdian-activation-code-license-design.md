# opub 爱发电激活码授权设计

## 背景

`opub` 已经实现一次付费、单设备绑定和 Ed25519 离线许可证，但当前支付流程依赖
面包多 Pay 动态创建订单、订单查询和 Webhook。创作者暂不满足面包多开通条件，
因此该支付依赖无法投入使用。

爱发电的“售卖商品”可以预先导入一批激活码，并在用户完成微信或支付宝付款后
随机发放一个。opub 可以把这些激活码视为一次性 bearer secret：服务端只签发
自己生成且尚未兑换的激活码，不需要获取付款人账号，也不需要在第一阶段接入
爱发电 API 或 Webhook。

本设计取代 `2026-09-05-device-bound-one-time-license-design.md` 中的面包多支付部分，
保留其设备指纹、本地许可证、Ed25519 签名、发布前门禁和不支持换机迁移等规则。

## 已确认的产品规则

- 目标用户是懂一点技术的个人创作者和一人公司。
- 商品采用“大版本单次买断”，不做订阅或自动续费。
- 首发商品为 `opub 0.x 创始版`，售价人民币 9.90 元。
- 一次购买获得一个激活码，首次兑换时永久绑定一台设备。
- 许可证永久允许使用 opub `0.x`；未来大版本不在本次授权范围内。
- 换电脑视为新设备，必须重新购买；不支持解绑、迁移或人工重置。
- 暂不要求创作者完成爱发电认证，先使用同批测试码跑通授权闭环。
- 不建设 opub 用户账号，不保存付款人的姓名、手机号、邮箱或爱发电身份。

## 方案选择

采用“爱发电随机发码 + 自建兑换接口 + 本地签名许可证”。

完整生产流程：

```text
opub 服务端生成一次性激活码
  -> 将明文激活码批量导入爱发电商品库存
用户在爱发电使用微信或支付宝付款
  -> 爱发电从库存随机发放一个激活码
用户在 opub 中提交激活码
  -> 服务端核对激活码并原子绑定当前设备
  -> Ed25519 签发设备许可证
opub 本地验签并保存许可证
  -> 后续发布永久离线验证
```

未认证阶段使用同一条兑换链路，但由开发者直接取一个库存测试码交给客户端，
不经过真实付款。以后完成爱发电认证并上架商品时，只需上传同一格式的未使用码，
客户端和许可证服务不需要改变。

### 未采用的方案

- **爱发电 Webhook 直接匹配设备**：爱发电订单通知包含订单和付款人信息，但没有
  为 opub 动态创建支付订单的接口，无法天然知道应绑定哪台设备。使用订单留言
  传设备码容易因漏填、错填而产生售后。
- **付款后粘贴爱发电订单号**：可以通过 API 验单，但用户需要寻找并复制订单号，
  操作比平台直接发放激活码更复杂，服务端还需长期保存爱发电 API Token。
- **爱发电 OAuth 绑定**：体验较完整，但需要应用接入、授权回调和用户身份关联，
  与“不做账号体系、先跑通功能”的目标不符。
- **继续使用面包多 Pay**：创作者目前不满足开通条件，无法完成真实支付闭环。

## 信任边界

服务端不验证爱发电订单。付款证明由“持有一个由 opub 服务端生成、尚未兑换的
高熵激活码”代替。生产环境中的明文码只交给爱发电库存，由爱发电在付款后发放。

因此必须满足：

- 每个码至少包含 128 位密码学随机量。
- 数据库只保存激活码的带域分隔 SHA-256 哈希，不保存明文码。
- 日志、HTTP 响应和错误信息不得回显完整激活码。
- 同一个码只能首次绑定一台设备。
- 同一码在原设备重复兑换必须幂等返回原许可证。
- 同一码在另一设备兑换必须拒绝，且不能改变原绑定。
- 已有许可证的设备再次提交新码时返回现有许可证，不消耗新码。

此设计仍属于诚实用户门禁。公开 Python 包中的本地检查可以被有意修改，产品价值
主要来自可信发布、持续平台适配和便利性，而不是强 DRM。

## 商品与版本

商品标识改为 `opub-major-0`，许可证载荷仍使用 schema 1：

```json
{
  "schema_version": 1,
  "key_id": "签名密钥版本",
  "license_id": "随机 ID",
  "product": "opub-major-0",
  "device_hash": "SHA-256",
  "issued_at": "ISO 8601 时间"
}
```

客户端 `0.x` 只接受 `opub-major-0`。未来 `1.x` 使用新的商品标识和许可证规则，
不影响用户继续运行已经安装的 `0.x`。

爱发电商品配置：

- 商品名：`opub 0.x 创始版`
- 型号：`单设备永久许可证`
- 售价：`9.90 元`
- 交付：随机发放一个激活码
- 商品描述明确设备绑定、版本范围和不支持迁移

```text
https://afdian.com/item/69bf71f0a9f511f1bc065254001e7c00
```

## 激活码格式与库存

激活码使用 Crockford 风格的大写 Base32 字符集，移除容易混淆的 `I`、`L`、`O`、
`U`，建议展示格式：

```text
OPUB0-ABCDE-FGHJK-MNPQR-STVWX-YZ234-56789
```

分隔符只用于输入可读性。客户端和服务端在校验前统一转成大写并移除连字符；
除规定字符和格式外的输入直接拒绝。码生成器同时完成两项工作：

1. 在数据库中导入码哈希和商品标识。
2. 将明文码写入权限为 `0600` 的输出文件，供开发者上传爱发电库存。

同一次批量操作必须使用数据库唯一约束防止碰撞。明文文件上传完成后由开发者决定
何时删除；程序不会把明文码提交到版本控制。

## 数据模型

新增 `activation_codes` 表：

```text
code_hash       TEXT PRIMARY KEY
product_id      TEXT NOT NULL
status          TEXT NOT NULL       available | redeemed
created_at      TEXT NOT NULL
redeemed_at     TEXT NULL
device_hash     TEXT NULL
```

新增 `code_licenses` 表：

```text
license_id      TEXT PRIMARY KEY
code_hash       TEXT UNIQUE NOT NULL REFERENCES activation_codes(code_hash)
device_hash     TEXT UNIQUE NOT NULL
signed_payload  TEXT NOT NULL
issued_at       TEXT NOT NULL
```

现有 `orders` 和 `licenses` 表保持原结构，以便回滚和审计。这样无需重建带外键的
旧表，也不会让数据库迁移依赖“生产库一定为空”的假设。新激活流程只读写
`activation_codes` 和 `code_licenses`。激活码兑换与许可证创建在一个
`BEGIN IMMEDIATE` 事务中完成，防止两个设备并发兑换同一码。

## 服务接口

新增并作为主要激活接口：

### `POST /v1/code-activations`

请求：

```json
{
  "device_hash": "64 位十六进制 SHA-256",
  "activation_code": "OPUB0-...",
  "client_version": "0.7.0"
}
```

成功响应：

```json
{
  "status": "licensed",
  "license": {
    "payload": {},
    "signature": "..."
  }
}
```

处理顺序：

1. 严格校验设备哈希、客户端主版本和激活码格式。
2. 计算带域分隔的激活码哈希并查询库存。
3. 未找到时返回统一的无效码错误。
4. 已绑定本设备时幂等返回原许可证。
5. 已绑定其他设备时返回“激活码已使用”。
6. 若传入码可用但设备已有许可证，返回现有许可证且不消耗新码。
7. 可用码和新设备在同一事务中完成标记兑换、创建并保存签名许可证。

接口采用每 IP 与每设备双重限流，防止枚举激活码。失败响应不区分“码不存在”和
“格式合法但库存无此码”的内部细节。完整激活码不能进入访问日志或应用日志。

旧的动态付款接口和面包多 Webhook 从运行入口移除：

- `POST /v1/activation-sessions`
- `GET /v1/activation-sessions/{session_id}`
- `POST /v1/webhooks/mianbaoduo`

如果保留旧代码用于历史参考，也不得在生产 FastAPI 应用中注册这些路由，且部署
配置不再要求面包多密钥。

## CLI 与 Agent 行为

CLI 提供：

```bash
opub --license-status
opub --activate
opub --activate --code OPUB0-...
```

`--activate` 在交互终端中的流程：

1. 已有有效许可证时直接成功退出。
2. 打开固定的爱发电商品地址。
3. 提示用户粘贴爱发电发放的激活码。
4. 调用 `POST /v1/code-activations`。
5. 本地验证服务器签名及设备哈希。
6. 原子写入 `~/.opub/license.json`，权限为 `0600`。

`--code` 便于 Agent 和非交互调用。激活码只在首次兑换前有价值，文档仍应提示用户
购买后立即激活，不要公开未使用码。命令输出不得打印传入码。

Agent 发布流程：

1. 发布前运行 `opub --license-status`。
2. 未授权时运行 `opub --activate`，告知用户已打开购买页。
3. 用户提供激活码后运行 `opub --activate --code <code>`。
4. 激活成功后继续原发布任务，不重复收集视频、标题或平台参数。

不再询问微信或支付宝；支付方式由用户在爱发电页面选择。

## 错误与退出码

继续使用许可证失败退出码 `13`。保留：

```text
LIC-001  尚未激活
LIC-002  许可证损坏或签名无效
LIC-003  许可证属于其他设备
LIC-004  无法取得稳定设备标识
LIC-011  激活服务不可用
```

新增或替换激活错误：

```text
LIC-013  激活码无效
LIC-014  激活码已绑定其他设备
LIC-015  当前客户端版本不适用于该激活码
```

删除面向用户的“订单等待超时”和“支付订单验证失败”路径，因为客户端不再创建或
轮询支付订单。

## 管理工具

许可证服务提供仅限服务器本地使用的命令行工具：

```bash
python -m license_server.codes generate --count 100 --output /secure/path/codes.txt
python -m license_server.codes stats
```

`generate` 必须在输出文件已存在时拒绝覆盖，输出文件权限为 `0600`。`stats` 只显示
可用数、已兑换数和总数，不显示码、设备哈希或许可证内容。不提供远程管理接口，
避免为 MVP 引入后台登录和新的公网攻击面。

## 部署与测试阶段

第一阶段不要求爱发电认证或真实付款：

1. 在本地临时数据库生成测试码。
2. 使用测试码完成首次绑定。
3. 验证同设备重复兑换返回同一许可证。
4. 验证另一设备兑换同一码被拒绝。
5. 验证已授权设备离线发布门禁通过。
6. 验证构建产物不包含服务端代码、私钥或激活码明文。

第二阶段才进行生产接入：

1. 将新服务部署到 `https://dachitech.xyz/license`。
2. 在生产数据库生成正式库存码。
3. 将明文库存上传到爱发电商品的随机激活码交付设置。
4. 完成一次 9.90 元真实购买、发码、兑换和离线发布验证。
5. 确认爱发电结算和创作者认证要求后再公开推广。

## 安全与运维

- 许可证私钥和数据库只保存在服务器，继续每日备份。
- 激活码明文文件属于敏感库存，不进入 Git、日志、聊天记录或发行包。
- 购买 URL 和 Ed25519 公钥可以随客户端公开发布。
- SQLite 使用 WAL；兑换事务使用唯一约束和写锁保证一次性绑定。
- 服务器仅开放兑换接口，不暴露码生成、库存查询或许可证重签接口。
- 退款或投诉后不支持吊销已经离线签发的许可证，这一点写入商品说明。

## 验收标准

- 无爱发电认证、无真实付款时，可用预生成测试码跑通完整授权闭环。
- 一个未使用码首次兑换后只绑定一台设备。
- 相同设备重复兑换返回字节一致的许可证。
- 不同设备不能复用已兑换码。
- 已授权设备提交新码不会消耗新库存。
- 本地许可证丢失后可使用原激活码在原设备取回；没有原激活码时不提供人工找回。
- 发布入口仍在读取 Cookie、安装依赖或启动浏览器前拒绝无许可证用户。
- 有效许可证在断网状态下仍可发布。
- 服务端配置不再要求面包多 App ID 或 App Key。
- wheel 和 sdist 不包含服务端、私钥、SQLite 数据库或激活码明文。
